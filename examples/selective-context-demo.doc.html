About this document

This file is a doc.html v0.3 document. The format itself is the only dependency: no framework, no build system beyond a single Node script, no server required to read it.

It holds the Zephyr Stream API Reference — a fictional real-time data-streaming platform used here as a synthetic corpus. The corpus was chosen deliberately large: it contains 152 sections totalling 75,314 characters of section content. Loading all of it into a context window at once is wasteful when a reader needs only two or three sections at a time.

That wastefulness is the point. The manifest (the <nav id="manifest"> element below) lists every section with its title, summary, SHA-256 witness hash, and character count. A reader that consults the manifest first can identify exactly which sections are relevant, fetch only those by #id, and verify each one's integrity against its witness — never loading the rest.

Known scaling limit: this manifest is flat — one entry per section. At 200 sections it is already hundreds of lines. A hierarchical manifest (chapter → section → subsection) would compress the navigation surface dramatically and is the obvious next step. That is future work; it is noted here honestly so readers can plan around it.

The format spec lives beside this file, at SPEC.md — and in the format's own body at SPEC.doc.html. The witness law: SHA-256 over the raw UTF-8 inner bytes of each section; char-count is Unicode code points (Array.from(inner).length). Both are checkable offline with no network access.

Glossary: Stream

The top-level container for an ordered, append-only sequence of events. A stream has a name, a partition count, a retention policy, and optionally an associated schema. Streams are identified by their stream_id.

Glossary: Event

The atomic unit of data in Zephyr. An event consists of a data payload (base64 binary or JSON), an optional key used for partition routing, optional headers (arbitrary string key-value pairs), and a server-assigned offset.

Glossary: Offset

A monotonically increasing integer that identifies an event's position within its stream. Offsets start at 0. They are assigned by the server at append time and never reused, even after event eviction.

Glossary: Partition

A subdivision of a stream that allows parallel produce and consume. Events with the same key are routed to the same partition (consistent hashing). Consumers may be pinned to a partition or consume from all partitions.

Glossary: Producer

A registered credential and rate-limit context for a publishing client. Each producer holds a producer_secret used to authenticate append requests. Producers are bound to a single stream.

Glossary: Consumer

A registered read context that tracks an independent offset into a stream. Multiple consumers can read the same stream at different offsets without interfering with each other.

Glossary: Lag

The number of events between a consumer's current acknowledged offset and the stream's head (latest) offset. A lag of 0 means the consumer is caught up. High lag indicates the consumer is falling behind the ingest rate.

Glossary: Checkpoint

An explicit record of the last offset a consumer has successfully processed. Checkpointing is the mechanism by which at-least-once delivery is implemented: a consumer that restarts from its last checkpoint will re-read events between the checkpoint and the crash point.

Glossary: Schema

An Avro or JSON Schema definition registered in the account and optionally associated with a stream. When a schema is associated, producer-side validation rejects events that do not conform.

Glossary: Idempotency key

An optional string header (Idempotency-Key) on append requests. Within the idempotency_window_s, duplicate requests with the same key and the same request body are deduplicated — only the first is applied.

Glossary: Access-control list (ACL)

A set of principal-to-operation grants on a stream. Zephyr uses a default-deny model by default: only explicitly granted principals can perform the listed operations. Supported operations: read, write, admin.

Glossary: Principal

An entity (user or service account) that authenticates to Zephyr and is subject to ACL checks. Principals are identified by their principal_id.

Glossary: Broker

A Zephyr server node that holds partition replicas, handles ingest, and serves consume requests. Clients do not address brokers directly; the API gateway routes to the correct broker.

Glossary: Replica

A copy of a partition held by a broker. Each partition has a leader replica (handles reads and writes) and zero or more follower replicas (replicate from the leader for durability).

Glossary: Rebalance

The process of redistributing partition leadership across brokers, typically triggered by adding capacity or recovering from a broker failure. During rebalance, affected partitions experience a brief leadership transfer.

Glossary: Snapshot

A named record of a stream's head offset at a point in time. Snapshots do not freeze or copy event data; they provide a stable position reference for migration, backup, or diff operations.

Glossary: Retention

The policy that governs how long events are kept in a stream before being eligible for eviction. Configured via retention_ms. Note: eviction is best-effort — events may persist slightly longer than the retention window under high load.

Glossary: Head

The latest offset in a stream — the position one past the last written event. Reading from the head with wait_ms > 0 long-polls for new events.

Glossary: Long-poll

A read strategy where the server holds an open connection for up to wait_ms milliseconds, returning as soon as new events are available (or at timeout). Long-polling reduces unnecessary polling under low-throughput conditions.

Glossary: At-least-once delivery

The delivery guarantee Zephyr offers: every event written to a stream will be delivered to a consumer at least once. Consumers must be idempotent or use a deduplication layer, because a crash before checkpointing causes re-delivery of events since the last checkpoint.

Glossary: Exactly-once delivery (not supported)

Zephyr does not natively provide exactly-once delivery. Producers can avoid duplicate ingest using idempotency keys, but consumer-side exactly-once requires an external transaction coordinator.

Glossary: Throughput

The rate of data flowing through a stream, measured in events per second or bytes per second. Throughput is bounded by the rate limit of the producing credential and the broker's partition capacity.

Glossary: Cursor

An opaque string returned in paginated list responses as next_cursor. Pass it back as the cursor query parameter to retrieve the next page. Cursors are valid for 10 minutes after issuance.

Glossary: Request ID

A UUID returned in all API responses as the X-Request-Id header and included in error response bodies as request_id. Include it in support escalations to enable log correlation.

Glossary: Account

The top-level organizational unit in Zephyr. All streams, schemas, and principals belong to an account. Quotas (retained bytes, stream count, schema count) are enforced at the account level.

Glossary: Base64 encoding

The default encoding for event data payloads. Binary data is base64-encoded when appended and returned base64-encoded on read, unless the consumer requests JSON encoding.

Glossary: Event header

Arbitrary string key-value metadata attached to an individual event by the producer. Headers are not indexed and not searchable; they are carried opaquely alongside the event payload.

Glossary: Leader replica

The broker replica that handles all reads and writes for a partition. Each partition has exactly one leader at any time; followers replicate from it.

Glossary: Follower replica

A replica that copies events from the partition leader for durability. Followers do not serve client requests; they become eligible for leader election if the current leader fails.

Glossary: Leader election

The process by which a follower replica is promoted to leader when the current leader is unavailable. During election, the affected partition is briefly unavailable; producers receive 503 and should retry.

Glossary: API gateway

The public entry point for all Zephyr client requests. The gateway handles TLS termination, authentication, rate limiting, and routes requests to the correct broker. Clients always address the gateway, never individual brokers.

Glossary: Time-to-live (TTL)

The duration after which a resource is eligible for automatic purge. Used for snapshots (snapshot_ttl_days) and idempotency keys (idempotency_window_s).

Glossary: Quota

An account-level limit on resource consumption: stream count, schema count, retained bytes, producers per stream, consumers per stream. Exceeding a quota returns 429 or 507 depending on the resource type.

Glossary: Tenant

A synonym for account in Zephyr's multi-tenant architecture. Each account is isolated: its streams, schemas, principals, and data are not visible to other accounts.

Glossary: Partition key

The key field of an event, used to route the event to a deterministic partition via consistent hashing. Events with the same key always land on the same partition, preserving ordering relative to other events with that key.

Glossary: Event ordering

Within a single partition, events are strictly ordered by offset. Across partitions, there is no ordering guarantee. Consumers that require total order should use a single-partition stream or impose ordering via their event model.

Glossary: Durability

Zephyr replicates each event to at least two broker nodes before acknowledging a successful append. The replication factor is configurable (enterprise tier only); the default is 2.

Glossary: Replication factor

The number of broker copies maintained for each partition. Higher replication factors increase durability at the cost of write latency. Default is 2 (leader + 1 follower).

Glossary: Acknowledgement (ack)

Confirmation from the Zephyr API that an append batch has been durably written to the required number of replicas. A 202 response guarantees the data will not be lost under normal broker-failure conditions.

Authentication

All Zephyr API requests require authentication. Two credential types are supported:

API keys (account-level)

Account-level API keys are generated in the Zephyr dashboard. Pass the key in the Authorization header:

Authorization: Bearer zph_live_<key>

Account-level keys have access to all resources in the account and are subject to the account's ACL configuration.

Producer secrets (stream-level)

Producer secrets are issued by POST /streams/{stream_id}/producers and are valid only for appending events to the bound stream. Pass the secret the same way:

Authorization: Bearer zph_prod_<secret>

Producer secrets cannot list streams, manage consumers, or modify ACLs.

Pagination

All list endpoints (GET /streams, GET /schemas, etc.) return paginated results. Pagination uses opaque cursor tokens, not page numbers.

Request

Supply ?limit=N to control page size (default 20, max 100). On subsequent pages, supply ?cursor=<next_cursor> from the previous response.

Response

{
  "items": [...],
  "next_cursor": "c_01hxyz..." // null when no more pages
}

A null next_cursor means you have seen all results. Cursors are valid for 10 minutes; a stale cursor returns a 400 error. Re-fetch from the beginning in that case.

Rate limiting

Zephyr enforces rate limits at the producer and consumer level. The default is rate_limit_default_rps (1,000 req/s), overridable at registration time.

Response headers

Every response includes:

  • X-RateLimit-Limit — the current limit in requests per second.
  • X-RateLimit-Remaining — requests remaining in the current second.
  • Retry-After — seconds until the limit resets (present only on 429 responses).

Handling 429

When you receive RATE_LIMIT_EXCEEDED, wait for the Retry-After interval, then retry with exponential backoff (initial interval 1 s, multiplier 2, jitter ±10 %).

Idempotent appends

To prevent duplicate events caused by network retries, supply an Idempotency-Key header on POST /streams/{stream_id}/events:

Idempotency-Key: <your-uuid>

Within the idempotency_window_s (default 60 s), any second request with the same key and the same request body returns the original response without writing a duplicate. If the body differs, you receive IDEMPOTENCY_CONFLICT (409).

Choose keys that are tied to the logical operation, not a random UUID per HTTP call. UUIDs derived from a business transaction ID are a good pattern.

Long-polling for new events

Rather than polling GET /streams/{stream_id}/events in a tight loop, set wait_ms to have the server hold the connection open until new events are available:

GET /streams/{stream_id}/events?consumer_id=<id>&wait_ms=5000

The server returns as soon as at least one new event is available, or after wait_ms milliseconds (whichever comes first). On timeout, it returns an empty items array — resume polling immediately.

Maximum wait_ms is capped at consumer_long_poll_max_ms (default 30,000). Set your HTTP client timeout to at least wait_ms + 5000 to avoid premature client-side timeouts.

At-least-once delivery pattern

Zephyr guarantees at-least-once delivery. To ensure no events are lost on consumer failure:

  1. Read a batch of events.
  2. Process each event (apply to your downstream system).
  3. Only after successful processing, advance the checkpoint via PUT /checkpoint.
  4. If the consumer restarts before step 3, it will re-read and re-process events since the last checkpoint.

Your downstream processing must be idempotent, or you must deduplicate by event offset. Storing the last-seen offset in your database — updated atomically with the event application — is the standard pattern.

Schema validation workflow

Schema validation enforces that producers publish conformant events, catching integration errors early.

Steps

  1. Register your Avro or JSON Schema via POST /schemas. Record the returned schema_id.
  2. Create a stream with "schema_id": "<id>", or update an existing stream's schema association.
  3. Configure schema_validation_mode: strict (default) rejects invalid events; warn admits them with an annotation in the event header.

Validation errors

On a VALIDATION_FAILED (422) response, the details field contains an array of per-field error objects:

{ "field": "/data/price", "error": "Expected number, got string" }

ACL management workflow

By default (acl_default_deny: true), only principals explicitly granted access can read or write a stream.

Granting access

PUT /streams/{stream_id}/acl
{ "principal_id": "usr_alice", "operations": ["read", "write"] }

Granting admin

The admin operation is required to modify the ACL itself. Grant it only to trusted principals. The account owner always has implicit admin on all streams.

Revoking access

DELETE /streams/{stream_id}/acl/usr_alice

Revocation is immediate. In-flight requests from the principal complete normally; all subsequent requests fail with 403.

Stream migration using snapshots

Snapshots provide a stable offset bookmark useful for coordinating a migration without stopping producers.

Procedure

  1. Create a snapshot on the source stream: POST /streams/{source_id}/snapshots. Record head_offset.
  2. Create the destination stream with the same configuration.
  3. Replay events from the source from offset 0 to head_offset into the destination.
  4. Cut over producers to the destination stream.
  5. Drain any remaining events from source (above head_offset) into the destination.
  6. Delete the source stream once all consumers confirm they have caught up on the destination.

Migration tooling that automates this procedure is available as a separate CLI (not covered in this reference).

Error handling best practices

Parse the error code, not the message

The error field is the machine-readable code; the message is for humans and may change. Build retry logic against error codes, not message strings.

Retryable vs non-retryable

  • Retryable (with backoff): 429, 500, 503, 504.
  • Not retryable without change: 400, 401, 403, 404, 409, 410, 413, 422.

Escalating to support

For unexpected 500 errors, include the request_id from the error body when contacting support. This enables log correlation on the Zephyr side.

Reading metrics effectively

Throughput monitoring

Poll GET /streams/{stream_id}/metrics?window_s=300 every minute to track the last 5-minute ingest and consume rates. Alert when ingest_rps drops below your expected baseline (producer health) or when consume_rps drops significantly below ingest_rps (consumer falling behind).

Lag monitoring

GET /streams/{stream_id}/metrics/lag returns instantaneous lag per consumer. Integrate this into your SLO dashboard. A sustained lag increase indicates the consumer cannot keep up — scale horizontally or reduce processing time per event.

Error rate

The error_rate field in each MetricSample covers all error classes. A spike typically indicates a client-side misconfiguration (schema validation failures, rate limit bursts) rather than platform instability.

API versioning policy

The current API version is v1. The version appears in the base URL: https://api.zephyrstream.io/v1/.

Non-breaking changes (no notice required)

  • Adding new optional request fields.
  • Adding new response fields.
  • Adding new error codes.
  • Adding new endpoints.

Breaking changes (90-day deprecation notice)

  • Removing or renaming existing fields.
  • Changing field types.
  • Removing endpoints.
  • Changing error code semantics.

Breaking changes are introduced in a new API version (e.g. /v2/) and the prior version is supported for 12 months.
